# Master register data contract

The application maintains asset identities and month-level inspection schedules. It does not certify equipment safety, inspection completion or regulatory compliance.

## Current implementation caveats — 2 November 2026

This contract defines required behavior. The [full review](app-review-2026-11-02.md) found gaps: R1 clears independent concerns on unrelated saves; R7/R8 break evidence-preserving interchange after selected deletion or for unassigned reviews; R2/R3/R9 affect reviewed browser mutations and epoch-aware export; R4–R6 affect cleanup/recovery. These findings remain open under the [repair plan](superpowers/plans/2026-11-02-app-review-fixes.md). They do not change owner-approved rules-version-2 criteria or authorize dropping evidence.

## Existing interchange

The seven existing linked sheets remain supported: Assets, Inspection Plan, Technical Details, Notes & Actions, Review Items, Source Cells and Field Map. Import Decisions is optional. Original-layout mappings remain in `inspection_app/legacy_layouts.json`; header validation and source sheet selection remain authoritative. Permanent asset IDs are never regenerated because source rows move. Package membership alone is insufficient identity evidence.

Assets preserve description/name, family, original tag and asset number, Oracle description, field, plant, locations, unit, raw service status, record status, source sequence, pack, parent/source groups, source sheet and row. Blank raw fields remain blank; unknown is not equivalent to not applicable. Raw service text is retained without inferring operating safety. Canonical record status is Active or Archived.

Inspection rows preserve IDs, type (OSI/Internal), explicit Yes/No applicability, last and next months, last status, scheduling condition, review status/reason, original last/next values and category, source sheet/row/cells. Month precision is YYYY-MM; a real source day is checked before reducing precision. No day is invented. Internal applicability requires a recognized tank/vessel family or review of classification. Next preceding last generates review, not an automatic correction.

Technical details preserve field ID/label, value, explicit unit, original value and source coordinates. No unit conversions are inferred. Notes preserve ID, type, full text and source. Review rows preserve original values, reason, status and provenance. Source cells preserve value, Excel type, annotation, row role and coordinates. Field Map preserves each extraction destination and preservation policy. Original source files are immutable evidence. Formula text and missing cached values must remain distinguishable.

## Trust

Snapshot eligibility uses automatic quality criteria (rules version 2), not mandatory manual verification. A name, recognized family, record status, inspection plan and explicit applicability are required. An applicable inspection needs a valid next month or a recorded scheduling condition; no review-by month is required. Missing location and identifiers do not themselves block inclusion. Blank or Never last-inspection dates pass; ambiguous/invalid dates, next-before-last chronology, duplicate identifiers and incompatible internal inspections require checking. Overdue work remains visible as overdue, not as a data conflict. Imported placeholder Undated is not a scheduling condition.

Historical import date flags are retained as evidence but superseded by current rule results. Independent source concerns and incoming differences retain their review workflow. Missing/damaged archived workbooks and formula-cache issues are warnings, not snapshot blockers. Condition review-by is optional: blank or elapsed review-by months create no quality flag and are not core verification fields. A supplied value must still use valid YYYY-MM format. Open blocking issues exclude an asset; all exclusions, warnings and accepted exceptions are published. New manifests record `eligibility_basis: automatic_quality_checks` and `rules_version`; existing saved manifests are unchanged.

Manual verification is optional and distinct from Passed checks. It binds field content to an owner action, UTC time and evidence/rationale; changes invalidate only affected fields. Automatic eligibility never writes verification evidence or claims engineering certification. Incoming differences continue to preserve manually verified values and require review.

Issue lifecycle: open, resolved, accepted_exception, superseded. Resolutions are checked against the relevant content fingerprint. Correction history is distinct from inspection history. Edit tokens are never reused after removal/reimport/restore. Transactions include their correction events.

## Synthetic acceptance inventory

Use disposable fixtures for duplicate tags with conflicting location, legitimate similar descriptions at different locations, reused package identifiers, missing names, moved source rows, invalid calendar dates, month-only dates, inverted chronology, multiline/formula-like notes and missing formula caches. Expected outcomes are explicit review or rejection without source loss, never inferred identity or engineering corrections. Operational workbooks must not be copied into test fixtures or edited by tests.

Imported last/next date and chronology review items resolve automatically when their corresponding current inspection fields pass the relevant checks. Their original values and reasons remain stored and correction history is retained. The editor hides resolved review comments and does not require clearing the same imported issue twice. Independent source concerns remain active until addressed; this automatic resolution does not create manual field-verification evidence. Generated summary ownership is tied to its exact last generated text; a legacy boolean marker alone cannot authorize rewriting a later concern.

The owner-approved year-only batch action previews both last and next inspection dates on active, applicable inspections. Only a retained source value consisting of exactly four digits (apart from surrounding whitespace), with a nonzero year and no current normalized month, qualifies. It preserves the source year and sets January (`YYYY-01`). Blank values, two-digit years, ambiguous strings, existing months, archived assets and inapplicable inspections are unchanged. This is an explicit owner-chosen default, not recovered source evidence. Preview groups changes by year and includes remaining validation findings; apply requires a reason, creates a backup, checks the master revision and writes an atomic correction journal. Matching imported review items are reassessed. Revert restores the affected inspection/review data only while affected records remain unchanged. No manual verification is created.

## Owner-controlled deletion

Deletion is explicit and previewed. Clear asset register retains import evidence and history; reset working data purges all working tables and archived sources while preserving schema, the monotonic version clock, backup configuration, database backups and recovery ZIPs. Deletion controls do not run against operational data during development.

Import batch JSON may contain `coverage_dismissed` (reversible attention-list dismissal), `evidence_deleted` (import contents deliberately removed, minimal lineage retained for live assets), and `source_archive_deleted` (the original archive deliberately removed). Missing source archives still produce the existing source-evidence warning; these flags never suppress the source availability check or alter rules-version-2 snapshot eligibility. Consolidated identities resolve through aliases when deciding which lineage remains required. Recovery packaging permits intentionally removed archives, but continues to reject unexpectedly missing archives.

Reset rotates `backup_settings.data_epoch`. HTTP mutations from an earlier dataset are rejected until reload, restore preserves the current epoch, and browser drafts/reconciliation use the same generation. Browser appearance and backup configuration are retained. An optional internal `cleanup_receipts(token TEXT PRIMARY KEY)` table distinguishes committed file deletions from uncommitted operations. Complete journals are atomically published under `.cleanup-journals/` before managed files move to same-directory quarantine; startup restores uncommitted files or finishes committed removals. Cleanup receipts and schema/version counters are technical state, not retained owner records.

Cleanup protection alone can use an explicit incomplete-source fallback: recovery manifest `unavailable_sources` lists canonical source digests that cannot be provided, and `source_relocations` maps damaged/misnamed archive digests to the actual content hashes whose bytes are preserved. Availability is normalized against the final packaged files, including swapped archives. The database snapshot is unchanged. Restore reports missing-evidence warnings and does not suppress normal source-availability checks. Ordinary recovery downloads still reject unexpectedly missing or damaged sources. New omission-aware safety packages require this updated app; existing complete packages remain supported.

Pending managed-file cleanup is completed before changing the independent backup folder. If a quarantined file remains locked, the folder change fails with a retryable error and the prior folder remains authoritative.
