# Completed inspection reconciliation

Use Reconciliation to update existing master records after UT inspections. It does not create assets. For a uniquely matched asset, a blank or method-only scope can use its sole applicable master inspection. Multiple applicable scopes and explicitly mixed OSI/Internal scope remain unresolved. UT alone is never treated as engineering evidence of an inspection category.

1. Upload an `.xlsx` results workbook and preview the inspection batch.
2. Review the update-available, up-to-date, older-inspection and needs-review groups.
3. Filter the rows if needed, then choose **1. Prepare batch updates**. This stages date changes for unique exact matches without requiring individual confirmation of each row.
4. Open **2. Review and apply batch**, inspect the old and incoming values, and select individual updates or **Select all eligible updates**.
5. Apply the selected updates together. A backup is saved first. A stale master version or invalid/conflicting update rejects the transaction.

**Open master asset** on a matched row or inside its Review dialog opens that existing record in the master register. Date fields, service status, and both incoming remarks columns show all differing incoming or selected values alongside the saved master values. Tab markers identify each section containing proposed changes. Selected values are distinguished from incoming values still requiring review, with a **Back to reconciliation** button. Opening a preview does not change the asset or confirm a match. To apply without returning to reconciliation, review the checkboxes in **Apply reconciliation proposals here**, confirm the match, and choose **Apply proposed changes** in the asset footer. Save or discard manual edits first. Dates remain blocked unless the incoming inspection is done; the server checks the displayed asset version before committing. Remarks are retained as separate notes and identical notes are not appended again. Rows without a selected asset must be matched first.

The workbook needs an asset ID, asset number, tag or package column; an inspection type/scope column containing OSI/External or Internal; and date columns. Recognized date headers include Actual inspection date, Actual completion date, Last inspection date/month, and Next due date/month. Actual completion takes precedence over an older Last inspection date column. Dates must include an unambiguous year and month. The old Full Inspection Plan layout remains supported. The Full Inspection Plan sheet is used if present, otherwise the active worksheet, with headers in the first 15 rows.

Date updates require explicit completion in the incoming workbook. Recognized completion columns include UT Progress, UT Status, Inspection Status, Completion Status and UT Completed. Done, Completed, Complete, Finished and 100% count as completed; Yes/True count only in a dedicated Done/Completed column. Blank, unclear, incomplete or conflicting completion evidence blocks date changes. Report Issued alone does not confirm completion. This is enforced in both the review screen and the apply endpoint, including for previously saved reviews.

Batch proposals use actual/last inspection dates and explicit next due dates. Planned dates remain reference evidence and are never proposed as completion or next due dates. A missing next due date leaves the existing due date unchanged. Older source dates are retained as history and never proposed over newer master dates. The server rejects older last or next dates atomically, including requests from saved reviews or older clients. No interval is calculated. Genuinely invalid supplied dates, dates due before completion, duplicate rows, ambiguous matches and missing inspection scope require individual review. Correcting dates on such rows remains possible through the individual review editor.

Up to date means the supplied dates, service status and remarks already agree; it does not mean that an inspection is verified or that absent dates were filled. An unchanged row requires no Done evidence, manual match confirmation or write to the master. Done evidence is required only when changing inspection dates. Matching remarks are not proposed again; case, whitespace and whole-note grouping differences (combined versus separate notes) do not create review work. Complete matching paragraphs are also recognised inside longer master notes without discarding additional history. A single final sentence period is ignored. Arbitrary partial text and genuinely different wording still require review. Reapplying unchanged values does not allocate a correction revision. Changed fields retain normal verification invalidation and current quality rules.

The current workbook review and pending decisions are saved in this browser. Replacing it starts another batch; export the complete review CSV first to keep a reference copy. Applied changes retain correction history, including submitted workbook name, source sheet/row, original date values, scope and progress/report text. This does not archive the complete uploaded workbook. Keep the source workbook independently.

After a successful apply, fully reconciled items disappear from the default active list. Use **Completed · applied** to revisit them; their source rows, review exports and correction history remain retained. Applying only part of a row keeps it active until the remaining proposals are resolved. Completion is reassessed from current master values after refresh and browser reload.

In legacy campaign layouts, Last Insp Date is historical, and known non-date history markers (None, Never, NA, Check History) do not propose a new date. An older year-only historical value is left as reference when the master already has that year or a later dated inspection. Planned Insp Date remains reference evidence, even when UT Progress says Done.
